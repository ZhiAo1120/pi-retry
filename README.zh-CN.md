# pi-retry

一个轻量的 Pi 扩展，添加手动 `/retry` 命令：**不回溯会话、不重发原始请求**，直接从失败点续跑。

[English](README.md) | 中文

## 推荐搭配安装

本扩展解决「你想手动介入时如何精准续跑」。如果你的上游 API 经常抖动、希望**任务不被打断**，
请同时安装 [pi-resilient-retry](https://github.com/ZhiAo1120/pi-resilient-retry)：

| | pi-retry（本扩展） | pi-resilient-retry |
|---|---|---|
| 触发方式 | 手动敲 `/retry` | 自动，失败即重试 |
| 定位 | 精准续跑，不重放已完成操作 | 后台重试，任务不中断 |
| 重试次数 | 最多 3 次，超出即拦下并提示原因 | 不限（可配置） |
| 历史修复 | `/retry` 剥 id，`--deep` 连 reasoning 一起剥 | 仅在上游明确报告 ID 失效时剥 id |

两者生命周期钩子互不冲突，可同时安装。一个负责「不让任务中断」，一个负责「你想介入时精准续跑」，
互补而非替代。

## 安装

需要 Node.js 22.19 或更高版本。已在 Pi 1.0.0 上测试。

```bash
pi install git:github.com/ZhiAo1120/pi-retry
```

重启 Pi，或在已有会话中执行 `/reload`。

本地开发时直接加载检出目录，不要在 Pi 扩展目录里维护副本：

```bash
pi install /path/to/pi-retry
```

Pi 加载本地包时不会复制文件。**只保留一个安装来源**：重载前先移除之前通过 git/npm 安装的版本，
并把旧的 `~/.pi/agent/extensions/manual-retry.ts` 移出扩展目录。如果那个文件有本地改动，请先备份。

## 使用

助手回合失败或被中断后：

```text
/retry
```

该命令要求会话处于空闲且支持 UI（TUI 或支持 UI 的 RPC 客户端）。只接受两个可选参数
`--force` 和 `--deep`，在非 UI 环境中不执行任何操作。

Pi 内置的自动重试负责瞬态供应商错误；本扩展**不添加任何重试循环或退避策略**，也不修改全局重试设置。

## 重复失败保护

重试无法修复未改变的坏请求、无效凭证、耗尽额度或损坏的供应商路由。无限重复只会增加延迟和成本。

- 手动重试返回相同失败且无进展后，再次执行普通 `/retry` 会被阻止。已派发的检查点也不会重复发送。
- 在 `/retry` 启动的运行中，第一个重复的供应商错误会停止 Pi 的原生重试调度器。即使错误不断变化，
  单次手动尝试中也最多允许 **3 次无进展的供应商请求**。更低的原生重试上限仍然生效。
  SDK 内部传输层重试不计入此预算；`retry.provider.maxRetries` 请保持 Pi 的默认值 `0`。
- 原始错误会被保留。警告会建议检查速率限制/额度、凭证、请求与供应商路由，或失败的操作本身。
  停止使用 Pi 的正常中止路径；TUI 会把排队中的用户输入恢复到编辑器。
- 该保护只读取当前活动会话分支，因此能跨 `/reload` 和会话恢复存活，可识别旧的 retry 标记，
  也不会泄漏到独立分支。新的用户请求、成功的工具进展、变化的错误/参数或切换模型，都可以允许一次新的尝试。

## 请求修复

重试通常重发同一份历史，因此池化上游若返回了不同的 resource，可能永远拒绝该请求：
上一个 resource 生成的历史项 id 已无法解析。对于手动重试启动的那次运行，本扩展会修复出站的
Responses API 载荷：

- 默认模式只移除完整消息项和工具项的可选 `id`。消息正文、工具配对、`call_id`、`encrypted_content`
  以及**所有 reasoning 项都会保留**，模型得以保持跨回合的思考状态。
- `--deep` 会额外丢弃历史 reasoning 项。这是**有损操作**：模型丢失此前的思考，
  且 prompt 缓存前缀会改变。仅当默认模式持续被上游拒绝时才使用。
- 修复永不触碰普通请求、chat-completions 载荷，或由 `/retry` 以外方式启动的运行，
  并在运行结算时解除。每次修复尝试会报告一次移除计数。

当上游报告 resource 归属类拒绝时，重复失败警告会指名 `--deep`，而不是给出泛泛的路由建议。

### `--deep` 的代价

| 模式 | 移除内容 | 后果 |
|---|---|---|
| 默认 | 仅 `id` 字段 | 思考内容完整保留，模型记得自己想过什么 |
| `--deep` | 整个 `reasoning` 项 | 思考内容彻底消失，模型不记得之前想过什么 |

`--deep` 会让模型可能重复犯错或前后矛盾，且缓存失效导致该轮更慢更贵。所以它**必须手动显式开启**。

## 恢复行为

本扩展检查活动分支上最新的助手响应及其后的工具结果：

- 以 `error` 或 `aborted` 结束的助手响应可被续跑。
- 最新工具批次中失败的某个结果可被续跑，即使同批次另有结果成功。
- 成功的最终响应或新的用户请求会阻止更早的失败被重试。以终止性 stop reason 为准，而非过期的错误文本。
- 诊断性 shell 输出（如 `!git status`）、系统消息和会话元数据不会掩盖本可重试的失败。
- 由其他扩展发起的请求可被续跑，无需存在用户消息祖先。

对于供应商失败和工具失败，`/retry` 都保留当前检查点并注入一条隐藏的续跑消息。模型被要求检查当前状态
是否已有部分副作用，并只重试失败或未完成的操作。本扩展**从不导航会话树、不重放原始用户提示、
也不直接重新执行工具**。

这有意设计为 **尽力而为**，而非精确一次（exactly-once）的执行保证。Pi 的公开扩展 API 未暴露手动重试执行器。
由模型介导的续跑无法保证工具参数完全一致，也无法阻止每一个重复的外部副作用。
对非幂等操作，尤其是被中断的操作可能已在外部成功时，请先检查状态再重试。

## 开发

```bash
npm ci
npm test
npm run check
npm pack --dry-run
```

测试使用 Node 内置测试运行器，包含一个离线 Pi 加载器/会话检查，使用本地假模型且不执行真实工具。
`check` 对扩展做严格 TypeScript 检查（对照 Pi 官方声明），而不仅仅是导入剥离类型的源码。
依赖声明的内部实现通过 `skipLibCheck` 排除；扩展自身仍被类型检查。Pi 和 TypeScript 仅为开发依赖，
扩展**没有运行时依赖**。
